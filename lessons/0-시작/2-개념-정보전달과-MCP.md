# AI에게 정보를 "어떻게" 전달할까 — MCP가 나온 이유

> 이 강의를 관통하는 핵심 개념. 실습에 들어가기 전에 이 한 편을 읽고 가세요.
> 한 줄 요약: **정보는 "양"이 아니라 "구조"로 준다.**

---

## 1. 발표를 토씨 하나까지 외우면 오히려 망한다

발표를 준비할 때, 대본을 **토씨 하나 안 틀리고 통째로 외우면** 어떻게 될까요?
한 군데서 막히는 순간 그다음이 통째로 무너지고, 외우는 것 자체가 부담이 됩니다.

발표를 잘하는 사람은 반대로 합니다. **핵심 키워드 몇 개만 준비**하고, 나머지는
그 자리에서 **추론하고 연결**합니다. 슬라이드에 단어 몇 개만 있어도, 사람은
그 사이의 빈칸을 알아서 메웁니다.

우리는 **띄엄띄엄, 이빨이 빠진 정보라도 연결할 수 있는 능력**이 있기 때문입니다.

**AI 모델도 똑같습니다.** 모델은 단순 검색기가 아니라 **사람처럼 추론하는 존재**예요.
그러니 모든 것을 통째로 주입할 필요가 없습니다 — 오히려 역효과입니다.

## 2. "스타필드 안 A 레스토랑으로 와"

친구를 부를 때 우리는 "스타필드 안 A 레스토랑으로 와"라고 하지,
"집에서 나와 좌회전, 200m 직진, 3번 출구, 에스컬레이터…" 모든 골목을
하나하나 읊지 않습니다. **친구가 알아서 찾아옵니다.**

- **목적지 + (스스로) 길 찾는 능력** > 모든 경로를 다 불러주기
- AI에게도 **목적지와 탐색 수단**만 주면, 나머지 경로는 모델이 추론합니다.

## 2.5 친구의 머릿속 = AI의 머릿속

"안성 스타필드 A 레스토랑에서 11시에 만나자." 이 한마디를 들은 친구의 머릿속을
처음부터 끝까지 따라가 봅시다. 친구는 경로를 하나도 안 들었지만, **아는 패턴을
떠올리고 → 필요한 것만 그때그때 찾으며** 스스로 길을 냅니다.

**① 큰 그림 (아는 패턴을 떠올린다)**
"안성 스타필드까지 어떻게 가지?" → *"아, 지도앱 켜면 되지."* 이건 배운 적 없어도
아는 패턴입니다. 지도앱을 열고, 대중교통으로 갈지 차로 갈지 정해 출발합니다.

**② 도착해서 (구체적인 건 그때 찾는다)**
스타필드에 왔지만 내부 구조는 모릅니다. → 키오스크(안내도)에서 "A 레스토랑"을
**검색** → 몇 층 몇 호인지 **확인** → 그 층으로 **이동**해 도착.

친구는 스타필드 지도를 통째로 외우고 온 게 아닙니다. **"이럴 땐 이 도구"라는 패턴을
알고, 세부는 필요할 때 찾는** 것뿐입니다.

**AI도 정확히 이렇게 사고합니다.** "내 잔고 얼마 남았어?"라고 물으면, AI가 손에 쥔 건
MCP 도구 **3개**(검색·상세보기·호출)뿐입니다. 그런데 이걸로 충분합니다:

| 단계 | 친구 (스타필드) | AI (MCP) |
|---|---|---|
| 큰 그림 | "지도앱 켜야지" (아는 패턴) | "이건 KIS 도구로 되겠네" (아는 패턴) |
| 검색 | 키오스크에서 "A 레스토랑" | `검색` 도구로 "잔고" 관련 API 찾기 |
| 확인 | 몇 층 몇 호·가는 길 | `상세보기`로 파라미터·필요조건 확인 |
| 도착 | 그 층으로 가서 도착 | `호출`로 실제 잔고 조회 실행 |

### 왜 이렇게까지 비슷할까?
사람도 AI도 **모든 걸 외워서** 일하지 않습니다. 둘 다 이렇게 합니다:
1. **패턴 인식** — "이런 상황엔 이런 도구/방법" 을 경험에서 떠올린다 (지도앱 / MCP 도구)
2. **점진적 해결** — 세부는 미리 채우지 않고, 필요할 때 한 겹씩 찾아 좁힌다 (키오스크 검색 / catalog)

그래서 정보를 줄 때도 **다 외우게 하지 말고**(문서 통째), **패턴을 잡을 큰 그림 + 필요할 때
찾을 도구**를 주는 게 맞습니다. 334개 문서를 미리 안 줘도, AI는 도구 3개로 낯선 몰에서
길 찾듯 도달합니다. 이게 catalog(점진적 공개)가 사람의 사고와 닮은 이유입니다.

### 처음 보는 건물이어도, 길은 여러 갈래
스타필드가 없던 시절, 처음 초대받아 갔다고 해봅시다. 정확한 구조는 하나도 모릅니다.
그래도 우리는 길을 찾습니다 — *"이런 대형 몰이면 분명 키오스크(안내도)가 있겠지"*,
없으면 *"인포메이션 데스크에서 물어보면 되지"*. 기존 패턴과 **완전히 일치하지 않는
상황**이어도, 일반적인 경험에서 추론해 방법을 만들어 냅니다.

핵심은 이겁니다: **목표에 도달하는 길은 생각보다 여러 갈래**입니다. 세부 지시를 하나하나
다 주지 않아도 도달할 수 있습니다. 그래서 역설적으로 —

> **너무 많은 정보를 한 번에 주면, 오히려 헷갈림과 착오가 늘어납니다.**

길이 여러 개인데 334갈래를 전부 읊으면, 듣는 쪽은 어느 길로 갈지 **더 헤맵니다.**
믿고 목표와 도구만 주는 편이, 다 알려주려 애쓰는 것보다 정확할 때가 많습니다.

## 3. 그래서 API 문서를 통째로 던지면 왜 안 되나

"KIS 문서 334개를 그냥 다 복붙하면 되지 않나?" → 오히려 나빠집니다.

- **토큰 폭발**: 전체 스펙이면 수십만 토큰. 매번 넣으면 비용도, 남는 공간도 없음
- **정확도 하락(lost in the middle)**: 정보가 많을수록 중간을 놓침 → **파라미터를 지어냄(환각)**
- **문서 ≠ 실행**: 다 읽어도 인증·헤더·계좌 처리 같은 실행은 문서만으론 안 됨
- **금방 낡음**: 복붙한 순간부터 원본과 어긋나기 시작

> **양(quantity)으로 한 번에 다 던지는 것**은, 발표 대본을 통째로 외우게 하는 것과 같습니다.

> **수업에서는 이 자리에서 화면을 하나 봅니다.** 강사가 API 도구(Apidog)로 KIS 를
> **직접** 불러 보여줍니다. 잔고 하나 조회하는 데 채워야 할 값이 **16개**입니다.
> 따라 하실 필요는 없습니다. 명세는 [`kis-api-맛보기.openapi.yaml`](../참고/kis-api-맛보기.openapi.yaml)
> 에 있으니 궁금하시면 나중에 열어 보세요. 다음 절의 MCP 로는 같은 조회가 **2개**가 됩니다.

## 4. MCP = 점진적 공개(catalog)

MCP는 이 문제를 **"필요한 것만, 필요할 때"** 로 풉니다. 이게 catalog(점진적 공개) 방식입니다.

- 평소엔 도구 **3개**만 보임 — `검색` · `상세보기` · `호출`
- 모델이 "아, 잔고 조회가 필요하네" → **그 스펙만** 그때 꺼내 로드 → 실행
- 334개를 미리 다 주는 게 아니라, **발표자가 키워드만 들고 있다가 필요할 때 세부를 꺼내는 것**과 똑같음

여기에 더해 MCP는:
- **구조화된 스키마**: 산문 문서가 아니라 타입이 정의된 형태 → 모델이 구조로 이해
- **실행 계층 내장**: 토큰·계좌·해시키를 서버가 처리 (AI는 "무엇을"만, "어떻게"는 서버가)
- **살아있는 소스**: API가 바뀌면 서버만 갱신 → 모든 클라이언트가 자동 최신
- **재사용(N×M→N+M)**: 서버 하나를 Claude Code·hermes 어디에나 붙임

## 5. 진짜 배울 것 — "정보를 전달하는 기술"

이 강의에서 도구 사용법보다 더 오래 남는 건 이겁니다:

> **AI에게 정보를 "어떻게" 주느냐가 곧 실력이다.**
> 많이 주는 게 아니라, **위계와 구조로** 준다.

핵심은 **무엇이 상위 의존성을 갖는 정보인지**를 먼저 생각하는 것입니다.
정보에는 위아래(의존 관계)가 있습니다.

- **인증/계정**이 가장 위 — 이게 없으면 그 아래 아무것도 못 함(모든 게 여기에 의존)
- 그 아래 **계좌** → 그 아래 **종목** → 그 아래 **세부 파라미터**

그래서 잘 전달한다는 건: **먼저 알아야 하는 상위 정보를 앞에 두고, 세부는
필요할 때 꺼내 쓰게** 구조를 잡는 것입니다. MCP의 catalog가 정확히 이 순서로
설계돼 있고요. 이 감각은 MCP뿐 아니라 **프롬프트·컨텍스트 설계 전반**에 통합니다.
그래서 **익숙해져야 하는 기술**입니다.

## 6. CLI는 뭐고, 언제 MCP보다 나을까 (그리고 왜 간략히만)

**CLI가 뭔가요?** 컴퓨터에게 **정해진 명령어를 글자로 쳐서** 시키는 방식입니다.
**자판기**를 떠올리면 쉽습니다 — 정확한 버튼(명령어)을 누르면, 정해진 결과가 딱 나옵니다.
빠르고 확실하지만, 버튼에 없는 건 안 되고, 어떤 버튼인지 정확히 알아야 합니다.

MCP는 반대로 **점원에게 말하는 것**에 가깝습니다 — "이런 게 필요해요" 하면 AI가
상황을 보고 알아서 골라 처리합니다.

**언제 CLI(자판기)가 더 나을까?**
- 할 일이 **매번 똑같고 정해져 있을 때**. 예) "매일 아침 9시에 이 조회를 실행" 같은
  반복은, 정해진 명령 하나가 제일 빠르고 확실합니다.
- 이미 잘 만들어진 명령어 도구가 있을 때.

**언제 MCP(점원)가 더 나을까?**
- 무엇이 필요할지 **미리 모를 때**. 예) "지난주 상황 보고 알아서 정리해줘" 처럼 AI가
  그때그때 뭘 볼지 판단해야 하면, 도구 상자(MCP)를 쥐여주는 게 낫습니다.
- 같은 걸 **여러 AI 앱에서 재사용**할 때.

> 한 줄: **정해진 반복은 CLI, 그때그때 판단이 필요하면 MCP.**

**그런데 왜 이 강의에선 간략히만?** CLI는 강력한 만큼 **위험**하기도 합니다(명령을
잘못 치면 파일이 지워질 수도 있어요). 안전하게 다루려면 한 단계 더 배워야 해서,
오늘은 **"이런 방식도 있고, 이럴 땐 이게 낫다"** 정도만 알고 넘어갑니다.
